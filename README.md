# Localnet

One Rust app for controlling Windows and macOS computers on your **trusted personal network**. The home screen is a gallery of computer names and screenshot previews. Click a computer to open its desktop across the window; **Computers** returns to the gallery. No accounts, pairing codes, approval dialogs, or cloud services.

## Interface

- Minimal dark desktop interface with installed system UI fonts (Segoe UI on Windows, system-font candidates on macOS, bundled egui fallback).
- Computer tiles show an aspect-correct screenshot and name. Screenshot previews refresh about every five seconds when the gallery is visible; unavailable previews show a placeholder with details on hover.
- Previews use separate screenshot-only requests and do not start a control session or initialize keyboard/mouse injection. On Mac they need Screen Recording, but not Accessibility. Full control still needs both permissions.
- A single outgoing preview worker, one cached incoming screenshot per five seconds, a 480x270 image bound, and a 256 KiB packet limit keep the gallery bounded. Errors retry more slowly. Hidden/minimized galleries stop requesting previews. Existing full sessions continue streaming if you return to the gallery.
- The remote screen uses the whole content area without a permanent sidebar or metrics panel. A compact header provides Computers, Disconnect, Full screen, and Settings. Click the remote image to control it. Returning to the gallery or opening Settings releases input.
- Windows extends the app header into the native frame, retaining DWM caption controls/hit-testing and native resizing. macOS uses a transparent full-size title bar with native traffic lights. Windows integration is tested locally; Mac title-bar placement and fullscreen still require native verification.
- Network, video, local-access controls, and OS permission tools live under Settings, not on the gallery.

## App Icon

The circular white Localnet mark is recreated as vector artwork in `packaging/icons/mark.svg`. `app-icon.svg` adds a restrained graphite rounded-square app tile. Checked-in PNG sizes (16 through 1024), Windows ICO, and macOS ICNS are generated by `powershell -ExecutionPolicy Bypass -File scripts/generate-icons.ps1` on Windows. The runtime PNG supplies the window/taskbar icon; `build.rs` embeds the ICO and Windows executable metadata. The Mac bundle script uses Apple's `iconutil` to build the Dock/Finder icon from the same PNGs before signing. SVGs are editable source references; the generator's geometry must be kept in sync when changing them.

No icon generator is needed for normal builds. Windows needs its installed SDK resource compiler (`rc.exe`), already part of the build tools; macOS uses the system `iconutil` tool. macOS Dock/Finder appearance still requires a native Mac build/run to verify. Updating a signed/ad-hoc bundle can invalidate existing privacy approvals.

## Trust Model

**Local access is enabled automatically while the app is open. Any reachable private-network peer can request screen viewing and keyboard/mouse control. Installing Localnet is not proof of device ownership.** Use only on a network where you trust every connected device. Do not expose the ports to the Internet, guest networks, shared Wi-Fi, or untrusted VPNs. Private IP ranges do not prove physical LAN membership, and Localnet does not enforce the Windows network profile.

TLS 1.3 encrypts connections and verifies the exact certificate received through discovery, but unauthenticated mDNS can be spoofed. This does **not** authenticate the intended computer against an active attacker. Transient, peer-bound, single-use session tickets coordinate the control/video connections internally; they are not user pairing credentials or an authorization barrier against a LAN peer. Nothing is stored in the clipboard or as a permanent access code.

**Settings > Disable local access** stops incoming access and discovery without closing outgoing sessions. **Disconnect everything and stop local access** in Settings, or closing the app, stops both directions. The app does not run at startup or install a background service, firewall rule, or cloud relay. While enabled, screenshot previews can be requested by other devices before a control connection is opened.

## Connect

1. Install the same **Localnet 0.4.0** build on Windows and Mac, then open both apps. Older builds are incompatible and appear as **Update required**. The versioned protocol now includes native Meta/Windows-key state; updating only the viewer does not update the Mac capture or keyboard backend.
2. Click a computer tile. The target starts sharing automatically, without typing a code or clicking Allow.
3. Click inside the remote image to send input. Use **Ctrl+Shift+F12**, **Release input**, or click outside the image to release remote input. Focus loss and disconnect also attempt to release held keys/buttons.
4. Click **Disconnect** when finished. Sharing ends automatically. The back arrow returns to the gallery without disconnecting the current session. Click the computer again to reopen it; a disconnected session is replaced, and clicking an existing connected computer selects it instead of launching a duplicate session.

Up to four outgoing sessions fit in one window; each target accepts one viewer. If a target is busy, the viewer receives a readable busy error rather than a silent reset. Inactive tabs still consume video bandwidth/CPU. Outgoing input pauses while someone controls this computer to prevent control loops; video continues.

Names and discovery certificates are unverified network data. The computer list is not saved. Discovery uses only the selected private interface and filters out this computer's interface addresses. Change interfaces under **Settings > Network**, then **Apply network**. Use **Enable local access** to resume after stopping it.

Windows Firewall must allow Localnet on **Private** networks. Discovery uses UDP **5353**, automatic connection startup TCP **45778**, and screen/input TCP **45777**. Wi-Fi client isolation, separate VLANs, firewall policies, and macOS Local Network permission can block discovery or connection. The app never changes these policies automatically.

## Windows Build

Requires Rust 1.92+, Visual Studio C++ build tools/Windows SDK, CMake, and NASM. CMake/NASM build a statically linked SIMD JPEG codec and are not runtime requirements.

```powershell
powershell -ExecutionPolicy Bypass -File scripts/build-windows.ps1
```

The build is `target/release/localnet.exe`. The packaged copy is `dist/Localnet-Windows.exe`, and the local per-user installation is `%LOCALAPPDATA%/Programs/Localnet/Localnet.exe` when installed. Updating the build does not automatically replace an already installed copy.

## Mac Build

Requires Rust 1.92+, Xcode Command Line Tools, and CMake (also NASM on Intel Macs). Build natively on the Mac; the Windows toolchain cannot generate the Mac executable.

```sh
sh scripts/bundle-macos.sh
open dist/Localnet.app
```

Install the app in a stable location, such as `/Applications/Localnet.app`, before granting permissions. Under **System Settings > Privacy & Security**, enable **Screen & System Audio Recording** (or Screen Recording) and **Accessibility** for Localnet. On macOS 15+, allow **Local Network** too. Use **Settings > Check Mac permissions** on the Mac for permission prompts, then restart Localnet. These OS permissions cannot be removed or bypassed by disabling application pairing. Viewing another computer does not need Screen Recording/Accessibility on the viewer.

Local builds are ad-hoc signed. Rebuilds can invalidate macOS privacy approvals. Set `LOCALNET_SIGNING_IDENTITY` to your Developer ID Application identity for signed distribution; notarization and stapling require your Apple developer account and are not done by the bundle script. Intended minimum macOS is 12, but a native Mac build and runtime testing are still required.

## Connection Errors

The earlier implementation could advertise a computer that was already sharing and then silently drop the discovery connection, producing Windows error **10054**. That is one code-supported cause, not a confirmed diagnosis of a particular Mac session.

The new version starts sharing off the UI thread, returns explicit permission/startup/busy errors, polls during slow startup instead of holding a three-second packet open indefinitely, and reports incompatible builds. Control admission/input initialization and video capture errors have explicit replies. The first observed terminal error is retained rather than always replaced by sibling-channel shutdown noise.

If the Mac still closes a connection, check the stage in the Windows error and the Mac's Localnet status in Settings. Confirm both copies are 0.4.0, close duplicate instances, grant OS permissions, and verify the firewall and selected interface. Native screen-capture calls are not cancellable by socket shutdown and can still block shutdown until the OS call returns. Unclaimed internal session tickets expire after 30 seconds; canceled startup results are discarded.

If connecting reports `invalid peer certificate: BadSignature` after the other app restarts, the discovered TLS certificate may be stale. Update the connecting computer, click **Refresh nearby computers**, then retry after the computer reappears. Certificate failures also trigger rediscovery automatically; the failed connection remains rejected. This is separate from Screen Recording or Accessibility permission. Refresh does not stop local sharing or disconnect existing viewers.

## Video and Input

- Windows uses persistent native DXGI Desktop Duplication with a reusable staging texture and screenshot fallback. Mac still uses xcap's deprecated screenshot API, not ScreenCaptureKit.
- Native libjpeg-turbo SIMD encoding/decoding uses reusable buffers and full chroma resolution for colored text. This is CPU JPEG acceleration, **not hardware H.264/HEVC/AV1**.
- Capture/encode, network receive, and decoding run independently. Each stage has one replaceable waiting frame plus the frame currently being processed; slow consumers take the newest frame instead of accumulating an old-frame backlog. Replacing stale frames is intentional and is counted in diagnostics, not a promise that every captured frame is displayed.
- The TLS video socket still has one request outstanding. The receiver requests again without waiting for decode. Terminal capture errors are sticky and sent only at a clean packet boundary; partial transport failures close the session without appending an error to a partial JPEG.
- Same-size desktop texture updates reuse existing GPU storage; size changes recreate storage. This reduces an avoidable allocation but is not zero-copy or hardware decoding. An extra RGBA clone after screenshot/resize is removed.
- Input uses a separate TLS/TCP connection with TCP_NODELAY. Adjacent pointer moves coalesce without crossing button events. Input batches and backlogs are bounded.
- Normal packet deadlines are three seconds, with 250 ms idle input heartbeats. Startup polls separately for up to 60 seconds. Partial packets terminate the session rather than replaying bytes.
- Retina/scaled pointer mapping uses host logical bounds separately from capture pixel dimensions and accounts for letterboxing.

Defaults are 1920px maximum width, quality 70, and a **60 FPS cap**, not guaranteed 60 FPS. Lower width/quality if slow and use Ethernet where possible. UI input ACK round-trip and receive/decode timings are not physical input-to-photon latency.

**Settings > Connection diagnostics** shows rolling received/decoded FPS, receive-wait and decode times, input ACK round-trip, replaced JPEG/image counts, texture-update count, and decoded-to-UI age. Receive wait includes host/network delay; received FPS may include static duplicates; UI updates are not actual display presentations. A smooth mouse on the target does not establish smooth returned video because input has its own connection. Mac screenshot capture, high-resolution Retina resizing, JPEG bandwidth, and Windows presentation can still limit smoothness. The pipeline changes require real Mac-to-Windows testing before claiming a specific FPS or latency improvement.

Previous local Windows release benchmarks at 1920x1080 measured original JPEG encoding around 72-75 ms versus native encoding around 12-15 ms, DXGI capture plus encoding typically 14-23 ms, and decoding/image conversion around 11-20 ms. These are small local pipeline measurements, not Mac/LAN/motion-video/60 FPS or near-zero-latency guarantees. A static desktop may reuse its last JPEG. Hardware encoding/decoding and ScreenCaptureKit remain future work.

On a Windows viewer, Ctrl still maps to Command on a Mac target and Ctrl on Windows. Windows/Super now maps separately to **Command on Mac / Windows on Windows**, including modifier-only transitions, Space, Tab, arrows, and letter chords. Modified letters preserve press/release state rather than becoming an isolated primary-modifier click. On a Mac viewer, Command retains its primary-modifier mapping and native Control/Alt letter chords are forwarded. Copy/cut/paste use the **remote clipboard**, not your local clipboard. Ctrl+C from Windows into a Mac terminal is still Command+C, not SIGINT.

The Windows-key hook exists only while remote input is active, checks the foreground window on each callback, ignores injected events, bounds its event queue, and is disarmed on release, native deactivation, gallery/settings/session changes, and shutdown. It does not record/log unrelated keystrokes or work outside the foreground Localnet viewer. Secure desktop, Ctrl+Alt+Delete, and Win+L forwarding are not implemented. Pressing Win+L exits forwarding; since the Win-down may already be suppressed, it is not guaranteed to lock locally. Release remote input **before** using local system shortcuts. Unsupported/OS-reserved combinations are not guaranteed. Hook failure leaves local input available with a UI warning; hook responsiveness and actual Command+Tab/Spotlight behavior still need physical Windows-to-Mac validation.

Full keyboard fidelity, non-US physical shortcut mapping, left/right modifier distinctions, IME behavior, and game-style key holds remain incomplete. macOS Accessibility is still required to inject Command/Control events.

Primary monitor only. No audio, file transfer, secondary monitors, login/lock screen control, Windows UAC secure-desktop, Ctrl+Alt+Delete, or control of elevated apps from a normal process. Protected content/cursor capture can be absent. Keep the target awake, signed in, and unlocked. Held input release is best effort when permissions or OS injection fail.

## Verification

This remains a prototype, not a hardened remote-desktop product. Windows loopback capture/network paths are testable here; Mac builds, real two-computer Windows/Mac sessions, and live input fidelity must still be verified on your hardware. Native codec internal allocations and the mDNS library cache are not enforced process memory budgets; protocol packets, UI device counts, batches, and decoded output dimensions are bounded.

With CMake/NASM available on PATH:

```sh
cargo fmt --check
cargo check --locked
cargo test --locked
cargo clippy --locked --all-targets -- -D warnings
cargo test --release --locked -- --ignored --test-threads=1 --nocapture
```

Ignored tests require an unlocked desktop/private LAN and capture frames to memory only. They do not inject keyboard/mouse input. Test permission denial/revocation, host busy, disconnect/reconnect, cable removal, app closure, display changes, Retina/Windows DPI corners, dragging out of the image, focus loss with held input, and native Mac permissions before normal use.
